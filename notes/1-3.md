# 1-3 實作三個工具函式與分派字典：把「說明書」接上「後端」

> 完成於 commit `b588be8`（前有自己的 WIP commit `1f1ddf4`，記錄了一次 NameError 踩坑）。

## 情境

1-2 給了模型一本說明書（`TOOLS`），模型也會遞申請單（`tool_calls`）了，但申請單遞來沒人受理——因為工具根本還沒寫。這一步就是把三個工具**真的做出來**：`read_file`、`list_dir`、`write_file` 三個 Python 函式，再用一個字典把「申請單上的工具名」對應到「該執行的函式」。

## 觀念

- **`TOOLS` 只是說明書，實作要自己寫**。三個函式＝「後端」，模型＝發請求的前端。對照：Swagger 文件（`TOOLS`）vs 真正的 handler（這三個函式）。模型的能力上限＝你給它的函式集合。
- **工具函式的回傳值一律是字串**。因為回傳值要塞回 `messages` 給模型讀，模型只讀文字；回傳 generator 之類的東西，`json.dumps` 會直接炸掉。連 `write_file` 這種「做完就好」的動作也要回 `"已寫入 {path}"`——不然模型不知道成功了沒。
- **函式的參數名必須跟 `TOOLS` 裡 `properties` 的 key 一模一樣**。因為執行時是用 `**kwargs` 依「名字」展開申請單上的 arguments——名字對不上就會 TypeError。說明書和實作是用「參數名」黏在一起的。

## 語法逐條（Python ↔ JS）

實際程式（`agent.py`）：

```python
from pathlib import Path

def list_dir(path):
    entries = Path(path).iterdir()
    names = [e.name for e in entries]
    return "\n".join(names)

def read_file(path):
    return Path(path).read_text()

def write_file(path, content):
    Path(path).write_text(content)
    return f"已寫入 {path}"

TOOL_FUNCTIONS = {
    "list_dir": list_dir,
    "read_file": read_file,
    "write_file": write_file,
}

# 執行申請單：
func = TOOL_FUNCTIONS[call["name"]]
func(**call["arguments"])
```

#### pathlib：把路徑包成物件再操作

Python
```python
Path(path).read_text()     # 讀整個檔回字串
Path(path).write_text(s)   # 寫字串進檔案（整個覆蓋）
Path("a") / "b.txt"        # 用 / 運算子拼路徑
```
JS
```js
fs.readFileSync(p, "utf8")
fs.writeFileSync(p, s)
path.join("a", "b.txt")
```
Python 把「路徑」當一種物件，讀寫拼接都是它的方法；JS 則拆在 `fs` 和 `path` 兩個模組裡。

#### iterdir：回的是迭代器，元素是 Path 物件

Python
```python
entries = Path(path).iterdir()
names = [e.name for e in entries]
```
JS
```js
const names = fs.readdirSync(p)   // 直接回字串陣列
```
兩個陷阱：`iterdir()` 回的不是 list（見下一條），而且元素是 **Path 物件**，要拿檔名得 `.name`。

#### iterator / generator：機器，不是裝好的盒子

Python
```python
it = Path(".").iterdir()  # 「會吐東西的機器」
list(it)                  # 需要盒子時再裝箱
```
JS
```js
[...iter]                 // 同概念：iterator 展開成 array
```
iterator 只能走一次、不能 `len()`、不能索引，換來的是**省記憶體**（不用一次全裝進來）。API 的 `stream: False/True` 是同一個概念：一次給整包 vs 一條條吐。

#### list comprehension：一行做 map

Python
```python
names = [e.name for e in entries]
```
JS
```js
const names = entries.map(e => e.name)
```
從迭代器逐項取值、組成新 list——Python 慣用 comprehension，角色就是 JS 的 `.map`。

#### join：黏合方向相反

Python
```python
"\n".join(names)
```
JS
```js
names.join("\n")
```
Python 是「**分隔符在前、list 在後**」，跟 JS 方向剛好相反——最容易寫反的一條。

#### 分派字典：值放函式本身，不加括號

Python
```python
TOOL_FUNCTIONS = {"list_dir": list_dir}
```
JS
```js
const handlers = { list_dir: listDir }
```
函式名不加括號＝「函式本身」這個值；加了括號就變成「現在執行、把回傳值放進去」。跟 JS 的 handlers object 完全同一招。

#### `**` 展開：依名字，不是依順序

Python
```python
func(**call["arguments"])   # {"path": "x"} → func(path="x")
```
JS
```js
fn(...args)                 // array 依「順序」展開
```
Python 的 `**` 把 dict **依名字**展開成具名參數；JS 的 spread 是**依順序**展開 array——這正是「函式參數名必須跟 TOOLS 的 key 一致」的原因。

#### f-string：字串插值

Python
```python
f"已寫入 {path}"
```
JS
```js
`已寫入 ${path}`
```

#### 無 hoisting：執行到才存在

Python
```python
print(x)   # NameError！
x = 1
```
JS
```js
hello()                    // OK：function 宣告有提升
function hello() {}
```
Python 的 `def` 和 `=` 都是「執行到那行才存在」，頂層在定義前使用會 NameError；JS 的 `function` 宣告有 hoisting，先用後定義沒事。

#### traceback：由下往上讀

Python
```
Traceback (most recent call last):
  File "agent.py", line 105, in <module>
    ...
NameError: name 'TOOL_FUNCTIONS' is not defined   ← 病名在最下面
```
JS
```
TypeError: xxx is not a function   ← 病名在最上面
    at ...
```
Python 錯誤訊息**病名在最下面**，跟 JS stack trace 相反——讀的習慣要倒過來。

## 踩過的坑（依序）

1. **`return Path(path).iterdir()` 直接回 generator**——塞進 messages 時 `json.dumps` 炸掉。教訓：工具回傳一律轉成字串。
2. **函式只做事沒 `return`** → Python 預設回 `None`，模型收到一片空白。
3. **測試碼放在檔案頂層、寫在 `TOOL_FUNCTIONS` 定義之前** → NameError（就是 WIP commit `1f1ddf4` 那次）。Python 沒有 hoisting，頂層測試碼要放最後，或包進 `if __name__ == "__main__":`。
4. **寫檔用 `./hello.txt`、讀檔卻用 `workspace/hello.txt`** → 路徑不一致，FileNotFoundError。相對路徑是相對「執行程式的位置」，不是檔案的位置。
5. **把多行 Python 直接貼進 zsh** → 終端出現 `if>` 續行提示等著你。程式碼要寫進檔案，用 `python3 agent.py` 跑。
